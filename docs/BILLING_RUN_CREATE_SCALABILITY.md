# BillingRun createTx — Scalability Design (P1, post-G6 hardening)

Status: **RC1+RC2 frozen decisions recorded — implementation gate HOLD,
production coding NOT authorized until this spec is reviewed.**
Source finding: G6 full-profile evidence (`docs/PILOT_CYCLE_1A_REPORT.md`)

## 1. Problem

`BillingRunService.createTx` generates **all** DRAFT bills for a period
in ONE Prisma interactive transaction — ≈8 queries × N settlements,
serial, bounded by Prisma's 5 s interactive-tx default
(`runAsTenant` passes no options).

Observed (G6, local PG, `watersaas_pilot`):

```text
500 settlements   PASS   (~2–4 s)
1000 settlements  FAIL   "Transaction already closed … 5000 ms"
4000 profile      unreachable without harness timeout
```

A real tenant above ~800 settlements/period cannot create a billing
run today. The pilot proved logic + data model at 4000 under a widened
budget; it did not prove the production transaction envelope.

## 2. Frozen contract to preserve

Pinned by `billing.e2e-spec.ts` + class docblock:

- `POST /billing-runs {period}` → **201 synchronous**:
  `status='DRAFT'`, `totalCount`, `successCount` (already-billed count),
  `failedSettlementIds[]`, `bills[]`.
- Per-settlement failures are **records, never aborts**
  (`TARIFF_NOT_FOUND`, `FEE_ITEM_NOT_FOUND`, `WATER_ACCOUNT_NOT_FOUND`,
  engine `DomainError`s); unexpected errors abort loudly.
- `billable=false` (MONITORING): skipped, outside the denominator.
- Already-billed (any run's NORMAL bill): skipped as success;
  `UNIQUE(tenant_id, source_type, source_id, bill_kind)` backstops the
  race; a lost unique race = resolved, not a failure.
- `discard`: DRAFT-only teardown; POSTED-side rows never deleted.
- `post`/`retry` (execute): claim tx → per-failure retry tx →
  per-bill post tx → finalize tx. Unchanged by this fix.
- Two DRAFT runs over one period: accepted operator-serial edge.

## 3. Decision history

- Options A (raise timeout) / B (bounded-batch multi-tx) / C (async)
  evaluated in the pre-RC1 draft. **RC1 approved Option B.** A remains
  an interim stopgap only; C stays deferred.
- RC2 (this revision): complete snapshot semantics, typed pricing
  snapshot, multi-tx idempotency primitives, key↔run FK lifecycle,
  exact fingerprint canon, finalization scale test.

# RC1/RC2 FROZEN DECISIONS — implementation spec

## A. Generation state — schema

```prisma
enum BillingRunGenerationStatus {
  GENERATING
  READY
}

model BillingRun {
  ...
  generationStatus BillingRunGenerationStatus @default(READY)
                   @map("generation_status")
  // needed as the FK target for idempotency_key (§G):
  @@unique([tenantId, id])
}
```

Migration backfills existing rows as `READY` (historical runs are fully
generated by definition).

New run row (TX0): `status=DRAFT`, `generationStatus=GENERATING`,
`totalCount=0`, `successCount=0`, `failedCount=0`,
`failedSettlementIds=[]`.

Only finalize transitions `GENERATING → READY`. `execute`'s claim adds
`generationStatus='READY'` to its guard — otherwise
`409 RUN_STILL_GENERATING`. `PROCESSING` remains reserved for the
post/retry pipeline; never reused for generation.

`BILLING_RUN_SELECT` + list/get responses expose `generationStatus`.
A GENERATING run is readable — its `bills[]` is an honest partial view.

## B. TX0 snapshot contract — `CreateSnapshot`

TX0 (`claimCreateTx`) captures, in one tx, **all** pricing inputs the
serial loop would read — nothing is re-read as authoritative later:

```ts
interface CreateSnapshot {
  runId: string;
  period: string;
  settlements: SettlementRow[];          // ordered FINAL rows (snapshot)
  accountFacts: Map<string, AccountFacts>; // usageCategory|settleAccountId|billable
  ytdBeforeQtyByAccount: Map<string, Prisma.Decimal>; // frozen ladder cursor
  dueDays: number;
  pricingByUsageCategory: Map<string, PricingSnapshot>;
  pricingFingerprint: string;            // sha256, §H
}
```

The snapshot lives **in the orchestrator's memory** for the request —
crash recovery is discard+recreate (§F); durable snapshot storage is
not required.

### B.1 Bulk YTD — `loadYtdBeforeQtyMap`

`ytdBeforeQtyByAccount` is a TX0 frozen input. Per-account
`ytdBeforeQty()` × N is forbidden. One set-based helper:

```ts
loadYtdBeforeQtyMap(tx, ctx, accountIds: string[], period)
  : Promise<Map<string, Prisma.Decimal>>
```

Semantics must equal today's `pricing.ts ytdBeforeQty` exactly — same
boundaries, same attribution rules, computed set-wide:

```text
1. NORMAL bills, sourceType=SETTLEMENT, posted-side
   (POSTED|PARTIAL_PAID|PAID), waterAccountId ∈ accountIds,
   period ∈ [YYYY01, current):
   → one findMany; then one findMany on the referenced settlements
   → per-account map<period, totalUsageQty>

2. REPLACEMENT bills, posted-side, same window
   → one findMany (id, period, waterAccountId)
   → one billItem findMany (qty NOT NULL)
   → per-account usageByPeriod[bill.period] += qty
   (PER_QTY-only is inherent: only items with qty count)

3. ADJUSTMENT bills, sourceType=RECONCILIATION, posted-side,
   period ≤ current:
   → one findMany ordered (waterAccountId, createdAt DESC, id DESC)
   → one billItem findMany (itemType=ADJUSTMENT)
   → one frozen-settlement findMany for accountIds over the window
   → per account: latest correction per parsed source period
     ('reconcile YYYYMM') replaces effective usage —
     corrected-set semantics identical to today's per-account loop
   (all queries filtered lte/gte boundaries exactly as today:
    adjustments use period ≤ current, settlements window [YYYY01,period))

4. ytdBeforeQtyByAccount[a] = Σ usageByPeriod.values() per account
```

≈6 queries total regardless of N (vs ~7N today). Batches never
re-read YTD.

### B.2 Typed pricing snapshot — `PricingSnapshot`

Per usageCategory present in `accountFacts`:

```ts
type PricingSnapshot =
  | { kind: 'READY';
      planId: string;
      effectiveFrom: Date; effectiveTo: Date | null;
      baseHousehold: number | null; perPersonQty: Prisma.Decimal | null;
      feeItems: FeeItemInput[];                  // loadFeeItems result
      feeItemIdByCode: Map<string, string>; }    // feeItemIdMap result
  | { kind: 'FAILURE';
      code: 'TARIFF_NOT_FOUND' | 'FEE_ITEM_NOT_FOUND';
      message?: string };
```

TX0 resolves each category once: `pickPlan` → `loadFeeItems` →
`feeItemIdMap`. `pickPlan` = null → `FAILURE{TARIFF_NOT_FOUND}`;
`loadFeeItems` BadRequest → `FAILURE{FEE_ITEM_NOT_FOUND}`. A per-
category pricing failure is **data, not an abort** — matching today's
per-settlement RecordedFailure semantics.

Batches consume the frozen snapshot; a settlement whose category is
`FAILURE` produces the corresponding `RunFailure{stage:'generate'}`
record. `computeBill` DomainErrors still surface per-settlement in
batches (usage-dependent — not part of the config snapshot).

## C. Bounded batch — `generateBatchTx`

`batchSize = 200` (const; env-tunable). Per batch, one `runAsTenant` tx:

```text
SELECT … FROM billing_run WHERE id=$run FOR UPDATE
assert status=DRAFT AND generationStatus=GENERATING
  (missing row → discarded mid-generation → abort request)
recompute pricing fingerprint from live config; assert == snapshot's
for each settlement in the batch slice:
  billable=false            → skipped++            (frozen accountFacts)
  already-billed probe      → success (skip)       (live — sibling runs)
  category FAILURE          → failure record       (frozen snapshot)
  computeBill(frozen inputs)→ bill.create + insertBillItems
                            + lockPlanForUpdate per bill (T8 unchanged)
  RecordedFailure/DomainError → failure record (in-memory accumulate)
  unique violation            → success (skip)
  unexpected                  → abort request loudly
commit
```

Failure records accumulate in the orchestrator and are written once at
finalization — not per batch.

## D. Finalize — `finalizeCreateTx`

One tx:

```text
SELECT billing_run FOR UPDATE
assert DRAFT + GENERATING
re-verify pricing fingerprint
recompute committed truth:
  drafted      = count(bill where billingRunId=run)
  failures     = accumulated records
  skipped      = accumulated
  totalCount   = settlements − skipped            (unchanged formula)
  successCount = totalCount − failures − drafted  (unchanged formula)
write totalCount/successCount/failedCount/failedSettlementIds
generationStatus = READY
idempotency completion (§G) commits in THIS tx
return withBills(run)
```

## E. Concurrent discard

`discardTx` accepts `DRAFT` in **either** generation state
(GENERATING or READY). Serialization is by row lock:

```text
batch tx holds run row FOR UPDATE → commits → discard acquires the
lock → deletes run + its DRAFT bills → next batch's assert
(run missing) → request aborts.
```

No generation batch may write after the run is discarded — the
FOR UPDATE + assert pair enforces it.

## F. Crash mid-create — recovery contract

No auto-resume in this P1:

```text
crash/unexpected error
  → DRAFT + GENERATING + partial DRAFT bills
  → post/retry: 409 RUN_STILL_GENERATING
  → discard: succeeds (releases linked PROCESSING key, §G)
  → re-create: already-billed probe absorbs leftovers
  → final bill set == clean uninterrupted create
```

## G. Idempotency — multi-transaction design

`runWithKey`'s one-tx claim+write+complete can't host multi-tx create.
The primitives move into `IdempotencyService` — no copied logic in
BillingRunService.

### G.1 Schema — `IdempotencyKey ↔ BillingRun`

```prisma
model BillingRun {
  id       String @id @default(uuid()) @db.Uuid
  tenantId String @map("tenant_id") @db.Uuid

  createIdempotencyKeys IdempotencyKey[]

  @@unique([tenantId, id])
}

model IdempotencyKey {
  ...
  tenantId     String  @map("tenant_id") @db.Uuid
  billingRunId String? @map("billing_run_id") @db.Uuid

  billingRun BillingRun? @relation(
    fields: [tenantId, billingRunId],
    references: [tenantId, id],
    onDelete: Restrict)

  @@unique([tenantId, key])
  // one BillingRun ↔ at most one create idempotency key;
  // PostgreSQL allows multiple rows where billing_run_id IS NULL
  @@unique([tenantId, billingRunId])
  @@index([tenantId, billingRunId])
}
```

Invariants enforced by the composite relation — **no `SetNull`**:

```text
billingRunId != null
  → linked BillingRun belongs to the same tenant (composite FK)
one BillingRun
  → at most one create IdempotencyKey (@@unique)
```

`ON DELETE RESTRICT` is defense-in-depth: discard unlinks/deletes keys
**explicitly** (§G.4) — an auditable domain action, not implicit
database behavior. A missed link blocks the run delete loudly.

### G.2 Service primitives (IdempotencyService)

```ts
// inside a caller tx: find-or-insert PROCESSING key
claimTx(tx, tenantId, meta: IdemMeta)
  : Promise<{ kind: 'NEW' } | { kind: 'REPLAY'; status: number; body: unknown }>
//   existing+mismatch → 409 KEY_REUSED_DIFF_REQUEST
//   existing+COMPLETED → REPLAY (verbatim stored responseRef)
//   existing+PROCESSING → 409 IDEMPOTENCY_IN_PROGRESS
//   insert unique race → IdemKeyRace sentinel (caller re-reads fresh tx)

// inside finalize tx: PROCESSING → COMPLETED + responseRef/status
completeTx(tx, tenantId, meta: IdemMeta, body: unknown): Promise<void>
//   responseRef = JSON.stringify(toJsonSafe(body)) — unchanged canon

// inside discardTx: delete PROCESSING keys linked to the run
releaseProcessingTx(tx, tenantId, billingRunId): Promise<number>

// fresh-tx lookup after IdemKeyRace (existing replayOrConflict, reused)
replayOrConflict(tx, tenantId, meta): Promise<IdemResult<unknown>>
```

Preserved verbatim: raw request-body sha256 hash, method, route,
`responseStatus=201`, the four-way key semantics, the unique-insert-race
→ sentinel → fresh-tx lookup path, `toJsonSafe` response canon.

### G.3 Orchestration

Controller passes the full `IdemMeta` (not just the key) to
`svc.create(ctx, parsed, meta)`. Orchestrator:

```text
TX0 claimCreateTx — ONE tx:
  claim = idem.claimTx(...)                       // NEW | REPLAY | 409
  if claim.kind === 'REPLAY' → return it; NO run, NO batches
  create billing_run {DRAFT, GENERATING, totals=0}
  write idempotency_key.billing_run_id = run.id   (key row exists → link)
  build + return CreateSnapshot

TX1..k generateBatchTx    (idempotency-transparent)

TXN finalizeCreateTx — ONE tx:
  …all finalize writes…
  idem.completeTx(...)   // COMPLETED + responseRef, same commit
  return withBills(run)
```

Claim result is a discriminated union — `NEW(snapshot)` /
`REPLAY(body,status)`; REPLAY short-circuits before any generation.

Crash matrix:

```text
crash before TX0 commits → rollback: no key, no run → retry safe
crash TX0..TXN           → key PROCESSING + run GENERATING, linked
                         → same-key retry: 409 IN_PROGRESS
                         → discard: releases key + deletes run
                         → same key reusable → fresh create
crash after TXN commit   → key COMPLETED + run READY → verbatim replay
```

No-key path: TX0 = run create + snapshot only; identical crash recovery.

### G.4 Discard lifecycle (frozen order)

```text
BEGIN

1. SELECT billing_run FOR UPDATE
   assert status = DRAFT

2. DELETE linked PROCESSING idempotency key
   DELETE FROM idempotency_key
    WHERE tenant_id=? AND billing_run_id=? AND status='PROCESSING'

3. Explicitly unlink COMPLETED key
   UPDATE idempotency_key SET billing_run_id=NULL
    WHERE tenant_id=? AND billing_run_id=? AND status='COMPLETED'

4. DELETE billing_run
   composite FK now clear; RESTRICT is defense-in-depth —
   an unexpected still-linked key/state fails closed

5. DELETE the run's DRAFT bill_items / DRAFT bills
   (existing discard contract, DRAFT-only predicate unchanged)

COMMIT
```

Result:

```text
PROCESSING key  → deleted → same key reusable
COMPLETED key   → survives, billingRunId=NULL
                  responseRef/status/hash/method/route unchanged
                  → same request still replays verbatim
unexpected linked key/state → BillingRun delete blocked by FK
                  → fail closed
```

## H. Pricing consistency — fingerprint

Canonical input per usageCategory (+ a FAILURE sentinel entry):

```text
usageCategory
tariffPlanId | FAILURE code
effectiveFrom / effectiveTo
baseHousehold / perPersonQty
feeItems[]: id, code, calcType
tiers[]:    tierNo, fromQty, toQty, unitPrice
dueDays (global entry)
```

Canonical serialization rules:

```text
object keys sorted; arrays in frozen order (feeItems by id,
tiers by tierNo); Decimal → string; Date → ISO; null preserved;
sha256 hex of the canonical JSON.
```

Recomputed from live config at the top of every batch tx and at
finalize; mismatch → request fails, run remains GENERATING →
discard/re-create. A `FAILURE` category's sentinel is part of the
fingerprint — a tariff appearing mid-generation is drift too and
aborts (operator discards + recreates on corrected config).
Account-side drift can't apply — the frozen snapshot is authoritative.

## I. Transaction ownership + controller

```text
public  create(ctx, body, meta)          TX_SELF_MANAGED orchestration
private claimCreateTx(tx, …)             TX_CALLER_MANAGED   (TX0)
private generateBatchTx(tx, …)           TX_CALLER_MANAGED   (per batch)
private finalizeCreateTx(tx, …)          TX_CALLER_MANAGED   (TXN)
```

- `createTx` removed as public entry; its internals move into the
  private tx methods. tx-registry: `BillingRunService.createTx` →
  `BillingRunService.create` (SELF_MANAGED); private tx bodies are
  only invoked from orchestrator-managed txs.
- Controller drops the single-tx `withOptionalIdem` for this endpoint —
  the orchestrator does claim/complete itself (§G). `withOptionalIdem`
  stays unchanged for payment etc.
- Pilot `flow.ts createBillingRun` → `svc.create(ctx, {period}, meta?)`
  (self-managed, no `withTenantTx` wrapper); `withTenantTxTimeout`
  removed once the regression proves the production path suffices.
